# 预测候选音频预算实验（PREDICTION_AUDIO_LIMIT）

生成时间：2026-11-18 23:25:33 +0800

本实验离线运行，不访问任何真实云接口。它用脚本化 Brain 和 fake Cloud 驱动真实的 `Session._predict`，固定文本到达和音频合成延迟。

## 模拟假设

- 10 条候选（5 个分支 × 每分支 2 条），文本到达时间 40–300 ms。
- 音频准备耗时 = 140 + 8 × 回复字数（ms）。
- PCM 字节 = 12000 × 回复字数（24 kHz PCM16，约 4 字/秒）。
- 各候选预合成并发执行，没有 TTS 排队；因此限制 N 不改变前 N 条各自的音频延迟，只改变哪些候选有音频、总字节数和预测任务等待的音频尾巴。
- 脚本化短答分别在 150 ms（音频尚未全部就绪）和 900 ms（所有文本和预算内音频都已就绪）评估。
- `预测任务完成 ms` 包含等待全部候选文字到达；音频预算只缩短其中的音频等待，不会让最后一条文字更早到达。

## 结论（由脚本生成）

- N=3：预合成 3 次 / 312.0 KB（all 的 100%）；900 ms 音频覆盖 3/10，脚本化音频命中 3/6；150 ms 发布覆盖 5/10；仅文本候选 7 条；回退 TTS 通过。

- N 档晚期音频覆盖随 N 增加：N=3 3/10。候选总数固定为 10，因此 N=10 与 all 在本实验中等价。
- 音频字节从默认档 all 的 312.0 KB 预算越小，节省的预合成字节和 TTS 调用越多，代价是更多候选命中后要临时合成。
- 早期发布覆盖最高的是 N=3（5/10）。默认档 all 在早期为 0：语音模式下所有候选都要等音频完成才发布；N>=1 时预算外候选会先以文本出现，但最早的那条候选仍在等音频。N=0 是例外：全部候选先出文本，所以最早发布覆盖最高。
- 仅文本候选的回退检查：1/1 个适用档位通过，均只调用 1 次普通 TTS，`audio_source=tts`、`prediction_audio_hit=false`、回复正常完成。


## 未实现 / 边界

- 这是合成负载，不是真实 TTS 并发、排队、网络抖动或真实候选命中分布；真实云接口一次都没有调用。
- 预测分支在实验中按固定到达顺序产生候选；生产里分支并发完成顺序可能不同，`前 N 条` 指实际到达顺序。
- 延迟用真实 `asyncio.sleep` 模拟，毫秒数有数毫秒抖动；本报告选择 150/900 ms 两个远离各候选就绪边界的检查点，档位结论不受抖动影响。
- 只比较音频预算，不模拟语音识别、模型选择、用户打断或播放时长。
- 默认（不设置 `PREDICTION_AUDIO_LIMIT`）仍保持原行为；本实验只验证实验档位。
