# 智语外呼项目｜三周开发计划与五人分工

> **项目目标**：在三周内完成一个可演示、可测试的任务型实时语音客服 Agent 原型，并展示基于评测反馈的策略优化闭环。  
> **团队配置**：5 人；A–D 负责核心研发，E 负责轻量展示与材料支持。  
> **建议演示场景**：电商订单配送异常通知与改约（具体业务以赛题要求为准）。

## 一、整体系统与开发范围

```text
用户语音
   ↓
[B] ASR / VAD / 轮次与打断处理
   ↓  用户文本
[C] 对话 Agent（LLM + Prompt + Workflow + Tools + State）
   ↓  回复文本 / 业务操作
[B] TTS / 语音播放
   ↓
用户听到回复

[A] 负责后端服务、接口、日志、通信、集成与部署
[E] 负责通话界面、状态与结果可视化

通话日志 + 工具记录 + 语音中间结果
   ↓
[D] 自动评测 → 错误归因 → Critic 提出改进 → 验证集对比
   ↓  验证通过后采用新配置；否则回滚
[C] 更新 Agent 的 Prompt / 策略配置（必要时代码改动人工审核）
```

**三周内优先实现**：单一业务场景、浏览器模拟外呼、实时语音对话、基本业务工具、通话记录、自动评测、受控的 Prompt/策略优化。  
**暂不作为必需目标**：自训练 ASR/TTS/LLM、真实大规模电话拨号、任意工作流代码的全自动改写、生产级并发部署。

## 二、五人分工总览

| 成员 | 角色 | 核心职责 | 主要交付物 | 工作量 |
|---|---|---|---|---|
| **A** | 后端与系统集成 | 设计模块接口；服务通信；会话、状态与日志管理；整合各模块；部署和稳定性 | 统一 API、后端服务、日志与部署环境、完整系统 | 较重 |
| **B** | 实时语音 | ASR 语音转文字、TTS 文字转语音；VAD/轮次检测；流式传输与打断；语音延迟和识别日志 | 可独立测试的语音模块、语音接口、打断功能与指标 | 较重 |
| **C** | 对话 Agent | 接入现成 LLM；设计 Prompt、工具、业务工作流；意图识别、业务状态、异常处理；支持版本化配置 | 文本版任务 Agent、工具调用、业务状态管理、可修改的策略配置 | 较重 |
| **D** | 评测与自主优化 | 构建开发/验证/测试案例；编写自动评测；错误归因（语音/Agent/工具）；Judge / Error Analyzer / Critic；验证门控 | 测试数据、评测脚本、错误报告、自动优化闭环、对比实验 | 较重 |
| **E** | 可视化与材料 | 简单演示页面；显示通话与业务状态、评测结果；准备测试材料、PPT、演示视频 | 可操作 Demo 页面、截图/视频、演示与答辩材料 | **较轻** |

### A｜后端与系统集成
- 建立代码仓库、开发环境和统一接口规范。
- 连接 B 的语音输入输出、C 的 Agent、D 的评测模块，以及 E 的展示页面。
- 负责会话 ID、业务数据、日志、错误处理、版本标记与部署。
- **边界**：不重复开发 ASR/TTS 或 Agent 内部策略；重点保障模块通信与整体稳定性。

### B｜实时语音模块
- **ASR**：麦克风/测试音频 → 实时文字；提供识别结果与时间戳。
- **TTS**：Agent 回复文字 → 合成、播放语音；尽量支持流式输出。
- **VAD/轮次检测**：检测说话开始与结束，避免抢话或长时间等待。
- **打断处理**：用户插话时停止播报、取消或协调取消当前回答，启动新一轮输入。
- **性能与评测支持**：记录识别结果、延迟、打断事件、播放状态；支持复现音频测试。
- **边界**：不负责业务 Prompt、工具设计，也不需要训练语音模型。

### C｜对话 Agent 模块
- 接入可用的 LLM，先完成**纯文本模式**下的任务流程。
- 设计客服场景的 System Prompt、意图处理、状态机/工作流及业务工具（如查询订单、提交改约申请）。
- 正确维护对话状态：用户改口、取消、拒绝、工具报错等情况要合理处理。
- 将 Prompt、规则与部分策略做成**可版本化配置**，便于 D 自动提出候选修改并验证。
- **边界**：不负责 ASR/TTS，也不负责制定最终评测基准；与 D 共同决定允许自动修改的范围。

### D｜评测与自主优化模块
- **第一周就能开始**：定义任务成功标准，准备开发集、验证集和最终测试集；实现自动检查结果与工具调用的评测脚本。
- 接入 C 后批量运行文本测试；接入 B 后运行语音端到端测试。
- **评测方式**：优先用程序检查业务结果/工具参数；对礼貌性、合理性等使用 LLM Judge；抽样人工审核 Judge 是否可靠。
- **错误归因**：对比“正确文本直接输入 Agent”和“音频经 ASR 再输入 Agent”，结合日志区分 ASR、VAD、Agent、工具、TTS 等问题。
- **优化闭环**：Judge 评分 → Error Analyzer 诊断 → Critic 提出 Prompt/策略修改 → 在验证集比较新旧版本 → 通过则采用，否则回滚。
- **边界**：优先实现受限的配置优化；不让 Critic 直接无限制修改工作流代码。代码级变更由 C/A 审核实施。

### E｜可视化与材料支持（轻量任务）
- 用简单的 Web 界面实现麦克风入口、通话文字记录、当前业务状态和最终结果展示。
- 展示 D 提供的关键评测指标及典型失败→改进案例。
- 协助整理测试场景、演示脚本、PPT、技术文档及录屏。
- **边界**：优先使用现成轻量框架，不承担复杂前端架构或核心算法开发。

## 三、三周里程碑

| 时间 | A（集成） | B（语音） | C（Agent） | D（评测） | E（展示） |
|---|---|---|---|---|---|
| **第 1 周：基础原型** | 建仓库、接口、日志规范，搭建后端骨架 | 跑通 ASR/TTS，初步实现 VAD | 做出能完成一个业务的文本 Agent | 设计指标、约 20 个开发案例，写基础评分器 | 做简单网页骨架，整理演示场景 |
| **第 2 周：业务闭环** | 完成模块联调、日志、工具与服务接口 | 实时交互、打断、基础延迟监测 | 完善工具调用、状态管理、异常分支 | 批量测试；自动 Judge 和错误分类；补充验证案例 | 接入实时对话与状态展示 |
| **第 3 周：优化与展示** | 集成优化、部署、排查稳定性 | 改善延迟、打断与识别稳定性 | 配合 D 维护可修改的 Prompt/策略版本 | Critic + Validation Gate；新旧版对照与语音归因实验 | 完成评测展示、PPT、演示视频 |

**里程碑验收：**

1. **第一周末**：文本 Agent 和语音输入输出分别跑通，接口约定明确。
2. **第二周末**：能完成一次完整的模拟语音客服任务，并保存对话、工具调用和业务结果。
3. **第三周末**：能展示完整 Demo、自动评测结果，以及至少一组经过独立验证的策略改进实验。

## 四、模块对接规范（建议尽早确定）

| 对接方 | 需要传递的信息 | 谁负责对齐 |
|---|---|---|
| B → C | 识别文本、会话 ID、轮次/打断事件 | A + B + C |
| C → B | 回复文本或文本流、回答 ID、取消/停止事件 | A + B + C |
| C ↔ A | 业务工具请求、工具响应、状态更新 | A + C |
| A/B/C → D | 会话日志、ASR 文本、Agent 输入/输出、工具轨迹、时间戳、版本号、测试音频引用 | A + D（B/C配合） |
| A/C/D → E | 通话状态、消息、业务结果、评测指标 | A + E |
| D → C | 错误类别、修改建议、新策略候选、验证结果 | C + D |

**注意**：日志里必须能看到“用户实际语音/人工参考转写 → ASR 文本 → Agent 输入/输出 → 工具调用 → 最终业务结果”，否则 D 很难正确定位问题。测试音频应在获得参与者同意后采集，并做好数据访问控制。

## 五、评测数据和优化原则

- **不训练底层模型参数**：数据主要用于模拟业务场景、发现失败、验证策略与最终测试。
- **数据建议**：先准备约 20 条开发案例，随后补充约 15 条验证案例和 15 条独立测试案例；另准备一批配有人工参考转写的语音样本。数量可按进度调整。
- **评测重点**：业务任务成功率、工具参数正确性、严重业务规则违规、语音识别和打断表现、端到端延迟。
- **优化重点**：Prompt 的重写与精简、业务状态更新规则、工具参数约束、有限的工作流分支与失败恢复策略。
- **版本原则**：一次修改形成一个候选版本，验证结果达标且无明显退化后采用；最终测试集不反复用于调 Prompt。

## 六、协作要求与最终交付

**协作约定**：每人维护独立模块和 README；第一周就确定 API；每天简短同步阻塞；每周至少联调一次；第二周末尽量冻结主要功能。

**最终交付清单**：

- [ ] 可操作的模拟语音外呼 Demo（单一完整业务场景）
- [ ] 实时 ASR/TTS、VAD/轮次检测、打断处理
- [ ] 可正确调用模拟业务工具的任务型 Agent
- [ ] 完整会话日志和结构化业务结果
- [ ] 文本评测 + 语音端到端评测及错误归因
- [ ] Critic 提案、验证门控和至少一次可复现的优化对比
- [ ] 源代码与 README、架构图、演示 PPT/视频

> **总体原则**：先把“语音能交互、Agent 能完成业务”做稳定，再实现自动评测，最后做可验证的自主优化。具体赛题要求与评分细则优先于此内部计划。
