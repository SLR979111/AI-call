# POP 整通任务 RSI 复测

这轮主指标是正常外呼的完整任务正确完成率。正常外呼一通必须完成开场自报身份、身份确认、沟通意愿、准确说明原因和整改、确认商家理解、结构化结果回写。追问也要答到点。工具调用的申请号、场景号、方式和沟通结果要正确，回执要与 SQLite 中唯一一条记录一致。错人、撤回、拒聊等压力用例按预期行为单独评分，正确退出不会计成已办成一通。

## 数据和来源

- 新增 72 通合成电话，正常 48 通、压力 24 通。开发、验证、最终留出各 24 通，每组四个业务家族，含 16 通正常和 8 通压力。按业务家族切分，检查原话规范化后没有与旧整通集或同批样本重复。旧版资料和公共业务知识均可用。
- 正常样本包括授权书资料、产品线、店名、证件、全球购、商标、行业资质等业务。正常追问基于两份工作簿中的操作路径、审核结果、材料要求和重复说明。压力样本加入代接、撤回、索要完整号码、催促承诺和未知日期。场景路由以定稿主表为准，54 条电话、14 条京麦。编号和商家均为测试数据。
- 新集有意使用旧整通集没有覆盖的口语表达。对话使用固定商家脚本，上一轮卡住也按脚本输入，能复现严格的流程通过率。正式泛化评估还需要可追问和可重说的模拟商家，以及有授权的真人录音。
- PDF 第 5–6 页列出三轮连续实时语音、首字 P50 不超过 2 秒、六段闭环和无严重违规的门槛。公开规则还列出任务完成、知识与工具、合规、语音、工程创新与协作。统一评分使用企业未公开数据，RSI 进化有效性是同分优先项。PDF 未给出逐项数字权重。业务补充材料来自《智语外呼-赛题说明.zip》及其中两份工作簿。

### WebRTC 语音

从验证和最终留出各抽一通正常对话，回放同一批 8 段商家合成录音。两组客服播报都使用 G2 的 DeepSeek `stella`，ASR 使用同一 DeepSeek 识别路径，分别从独立语音缓存启动。对照与候选分别完成 0/2 和 2/2 通，回写 0 条和 2 条。首声 P50 为 1.104 秒和 1.981 秒，P95 为 2.017 秒和 3.089 秒。相应轮次是同一输入。首声为录音末次有声帧至浏览器 Web Audio 首播，这几条均直接播答复，没有用过渡音计数。样本量不足以确认现场 P50。

固定同一候选，额外预热三条跨业务的常用答复。三条分别解释去京麦原申请查看书面意见、说明仍要复审、询问是否理解整改。第三轮仍完成 2/2 通、各回写一次。八轮合计首声 P50 降到 1.646 秒，P95 为 3.067 秒。两通各自的 P50 为 1.646 秒和 2.167 秒。后者的重讲和确认轮仍有较长等待，现场达标结论待实测。

上一版沿用身份、沟通意愿、复合确认和主动停止四项开关。这轮正常样本经常在沟通意愿阶段卡住，例如「这会儿能听，你说」被当成还需要询问是否方便。四项旧改动对这批样本的**整通**通过率没有净收益。

### 改动内容

1. **先判断当前阶段。** 原规则能确定的输入直接处理。模糊时 DeepSeek Flash 只返回意图和匹配当轮原话的证据。身份只认明确的身份确认，方便说只代表允许继续听，商家理解只有在已经解释清楚、没有新增问题时才可触发已有回写。支持「现在忙」和「刚忙完」按最新状态分别判断。未知、格式错误或超时回到原规则。
2. **先回答本轮追问。** 询问书面意见位置时解释怎么找这笔申请，询问处理方法使用当单整改，询问复审说明再次审核与结果边界。模型选择答复类别，回复使用当单资料和共有业务规则。回答后重新确认商家是否理解，原有回写和合规检查执行最终操作。

开发阶段用正常集选择候选，两组压力数据用于核验边界。锁定后才运行独立验证和最终留出。提示词只写阶段、证据、停止优先和澄清原则。候选采用 1,800 毫秒的模型预算。

### 典型对话与剩余错误

- 店名申请中，商家说「我这边能听，您说」。上一版继续问「您现在方便听一下资质审核结果吗」。候选把它理解为可以继续，说明当单店名问题和整改，商家明确知道怎么改后留下一条回执。
- 商家说「信号不太好，刚才那点能再讲一下吗」。候选重新说明该单的原因和动作，再等确认，避免用泛泛的「您想问哪一步」把用户拉回澄清。
- 最终留出有一通「店里这部分确实归我管」仍被判为身份不清，后续没有进入任务。验证集有三次模型调用超时。验证集一条询问从哪里看到新结果被标为审核类，实际回答了位置，冻结分数保留这项失败。
- 压力用例有一例承诺测试失败于评分。候选生成「这通电话不能保证通过，结果以复审为准」，合规规则把否定句中的「保证通过」命中后改成「以实际结果为准」。实际播出的答复仍无承诺，详细解释被截去。可用全新正反样本成对复核这一问题。

## 比赛创新方向

| 优先级 | 可以演示的能力 | 怎样证明有效 |
| --- | --- | --- |
| 1 | **失败后分段回放和归因。** 同一通先走音频，再用人工转写走同一对话策略。第三次用相同状态和明确的工具返回复盘。 | 用原话、实际转写、阶段、调用、落库组成失败证据。统计问题归因准确率、修复后整通净增和各阶段流失。答辩演示一次语音错轮和一次理解正确但回写失败。 |
| 2 | **围绕整通成功做预测缓存。** 优先准备会推进任务的下一步和商家常问的业务缺口。按预测顺序和预计节省的正文时间分配 TTS 名额。命中后仍校验阶段、当单及取消条件。 | 比较全生成、前 3 条和按收益限额。看正确整通数、有效命中、误命中、合成浪费秒数、首声和正文 P50/P95。用户改口、换材料或撤回时必须让旧候选失效。 |
| 3 | **会追问和改口的模拟商家。** 正常集按客服有没有解释到点继续行动。另用压力集挑战身份、过早回写和打断。 | 候选看不到商家预期。按家族留出验证，用不同措辞和同一业务流程检验泛化。把固定脚本和互动模拟分别计分。 |
| 4 | **可重放的工具故障与关单策略。** 回写失败明确告知，重试只产生一次记录，电话和京麦按业务历史分流。 | 用真实工具返回和持久记录逐项证实。演示连续重试、过早确认和异步打断后无重复回写。 |

## 复现

在仓库根目录执行。开发后选择 **grounded** 并冻结其指纹，再运行验证和留出。模型调用沿用原 Demo 的 DeepSeek Flash 配置，使用现有环境凭据。

```powershell
python -X utf8 scripts/run_pop_task_rsi.py --output data/rsi-task-v3-baseline
python -X utf8 scripts/run_pop_task_rsi.py --prior data/rsi-task-v3-baseline --output data/rsi-task-v3-development --splits dev
python -X utf8 scripts/run_pop_task_rsi.py --prior data/rsi-task-v3-baseline --output data/rsi-task-v3-independent --splits validation test --modes grounded
python -X utf8 scripts/run_pop_task_rsi.py --prior data/rsi-task-v3-baseline --output data/rsi-task-v3-repeat --splits validation --modes grounded
```

逐例评分、终端落库、合规重写和模型证据分别保存在上述目录。语音配置通过原 G2 的 DeepSeek `stella` PCM 合成和 G2 识别适配器接入同一 WebRTC 竞赛入口，G2 自身的预测和现有页面代码独立保留。

语音回放索引为 `data/rsi-task-v3-independent/voice-plan.json`，同批音频的哈希、各版本结果和首声见同目录 `voice-comparison.json`。在现有 `/rtc/` 通话页可用 `--g2-voice --rtc-pcm --prime-tts --prime-followup-tts --turn-intent grounded` 复现策略，并加载 `eval/pop/releases/closure-verified.v1.json`。本地时序演示的界面与此次提交的测试入口分别留存。

## 可追问模拟商家与多问题 RSI

本轮使用新的 60 通合成对话。12 个业务家族按开发、验证和最终留出切分，每组 12 通正常、8 通压力。同一业务文档也不会跨三组。模拟商家根据实际播出话术检查答案覆盖，只补问还没解决的问题，最多补问一次。仍未答全时不提供确认。正常任务分母固定为全部 12 通，回写必须对应已明确理解、真实工具成功和唯一 SQLite 记录。

对照是上一轮的 `grounded`，含阶段意图与单标签答复。两组候选都把追问拆成最多三个有原话证据的类别，再由当单资料组织答复。`plan-retry` 还允许在首次回写实际失败、商家明确要求后重试。重试使用同一个回写工具，停聊、撤回和下一轮新问题优先。候选都使用 DeepSeek Flash 和相同的 1.8 秒模型预算。首次试跑的 JSON 请求被接口拒绝，单条复现定位为 JSON 模式提示词须包含 “JSON”，补齐后才开始有效对照。

| 指标 | 验证 | 最终留出 | 两组独立集合计 |
| --- | ---: | ---: | ---: |
| 正常完整任务 | 10/12 → 12/12 | 12/12 → 12/12 | 22/24 → 24/24 |
| 正常首次答全 | 5/12 → 11/12 | 4/12 → 10/12 | 9/24 → 21/24 |
| 正常补问 | 7 → 1 | 8 → 2 | 15 → 3 |
| 压力正确处理 | 4/8 → 7/8 | 3/8 → 6/8 | 7/16 → 13/16 |
| 压力回写故障恢复 | 0/3 → 3/3 | 0/4 → 4/4 | 0/7 → 7/7 |

开发集正常任务保持 12/12，首次答全 4/12 → 11/12。两个候选均满足开发门控，带程序化重试的一组用了 54 次模型调用，另一组用了 57 次，因此锁定前者。独立集的模型调用总数由 111 减至 96。最终留出正常通过用例无退化，压力有一例退化，停止登记的请求未立即结束。候选保留在独立演示入口。现有压力程序评分的严重违规由 1 通降到 0 通，两通代接表达仍被放进下一阶段，评测均判失败。

例如商家问「这份授权我先补什么，补好了从哪儿传回去」。对照先讲要补的材料，商家得再问书面意见在哪儿。候选一轮同时给当单整改与京麦原申请入口。另一类问题是工具已经返回失败。新策略先明确告知这次没记上，再等商家说可以重试。实测有 7 通正确恢复且各留下唯一记录。

### TTS 名额回放

用开发日志统计首次答全且首句可以准备的情形，按重讲、入口、复审、整改排序。在两组独立集共 24 个正常追问上，以实际生成的首句逐字核对。已有 7 个可复用的首句。每通额外准备 1、2、3、4 条，分别新增覆盖 7、11、14、14 通。准备 3 条和 4 条覆盖相同，候选合成名额由 96 减到 72。此结果来自日志回放的名额估计，实时命中与首声使用独立的 WebRTC 证据。

### WebRTC 与归因回放

同一批两通、八段合成商家录音分别走原入口策略和锁定候选，双方启用相同的 DeepSeek ASR、`stella` 和通用预热，两边均实际各回写两条。加上双问题覆盖要求后，整通由 0/2 提到 1/2。首声 P50 从 1.174 升到 1.628 秒，P95 从 4.087 降到 2.941 秒。八个样本的 P95 等于最大值，本轮无法据此判断长尾稳定性。

行业许可那通的 ASR 保留了两个问题。参考原话和 ASR 转写在旧策略均只答到入口，新策略两者均答全。授权链电话里，「还要复审吗」被识别成「还要付什么」，候选对原话能回答授权和复审，对实际转写与语音都只答到授权。本轮留出的一通停止请求失败于模型超时后回到普通追问，须纳入下一版安全回归。

## 电话客服口语提示词

参考了三种语音交互实现。OpenAI 的客服示例将话风和业务工具分开，要求直接、简短、少复读。Vapi 的客服范例会把每轮提问控制在一个。Pipecat 的电话示例用短句、常用词和适合读出来的标点。这里采用的是这些电话客服规则。 [OpenAI 客服代理](https://github.com/openai/openai-realtime-agents/blob/main/src/app/agentConfigs/chatSupervisor/index.ts) · [Vapi 语音客服提示词](https://github.com/VapiAI/mcp-server/blob/main/skill/PROMPT_GUIDE.md) · [Pipecat 电话示例](https://github.com/pipecat-ai/pipecat/blob/main/examples/realtime/realtime-ultravox.py)

18282 主要由模型判断意图，由业务模板提供语音文本。口语版给 DeepSeek 每次一个回合的沟通目的和保留词，让它给两种能直接读出来的说法。对每条核对原意、业务动作、事实边界和问句数量，去掉模型额外添加的追问和重复状态。运行时从审核后的 `phone_style.v1.json` 读取文本。原话术及必说身份、结果、合规和回写仍走既有路径。

| 场景 | 原话 | 口语版 |
| --- | --- | --- |
| 查书面意见 | 您可以在京麦的这笔原申请里查看书面驳回意见。 | 您打开京麦，进入这笔原申请，就能看到书面意见。 |
| 确认下一步 | 您清楚这笔申请的整改办法了吗？ | 您清楚接下来怎么改了吗？ |
| 回写失败后询问 | 您要我再试一次记录吗？ | 您要我现在再试一次吗？ |

提示词在 `app/agent/pop_phone_style.py`，用 `scripts/draft_pop_phone_style.py` 离线生成候选。回归运行 `scripts/check_pop_phone_style.py`。WebRTC 启动时加入 `--phone-style eval/pop/phone_style.v1.json`，继续使用 `plan-retry` 和 DeepSeek `stella`。

同一策略回归 40 通，正常任务完整率保持 24/24，压力正确处理从 13/16 到 14/16。首次答全从 21/24 到 19/24，两条都有模板生成前的模型分类变化，原来是整改、复审或入口组合，本次将整改判为具体信息未知，随后补问办成。停止登记那条原来模型超时，本次成功。口语版对照保存这些波动，单次结果无法给模型波动定量归因。85 项 POP 功能回归通过。生成候选、审定话术和对照在 `data/rsi-phone-style-v1/`。

九组话术打乱版本做模型盲评，口语版 8 组获选、1 组打平，详细理由见 `blind-wording-review.json`。使用同一批 WebRTC 和 `stella` 录音回放，原版和口语版均有两条实际回写，逐通确认新话术已进入播报。八轮首声 P50 从 1.628 到 1.541 秒。口语版在 18283 独立演示。试听自然度仍可由真人判断。

### 手测反馈与修复

商家在「您清楚接下来怎么改了吗」之后说「不知道」。ASR 正确转写，原策略把短答当作信息不足的新问题，转去问材料、入口还是进度。现在只在核验后的结果确认阶段，将短否定直接接到本单整改和书面意见。重复短否定时，引导商家先打开京麦。实际 WebRTC 回放中，商家说「我不知道」时没有调用回写，说明法人证件整改后听到「清楚了」才记了一条。93 项 POP 相关回归通过。首批确认音频被转写成问句，记录保持空白。
